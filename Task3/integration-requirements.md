# PropDevelopment: требования к внешним интеграциям

Интеграция с платформой «Умный дом» партнёра выделена в отдельный контейнер `smart-home-gateway-app` (ACL) в домене ЖКУ. Это единая точка подключения партнёрских API для управляющего и событийного трафика: единые политики безопасности, нормализация модели данных, аудит операций. Медиа-канал домофона (WebRTC) устанавливается напрямую между мобильным приложением и платформой партнёра. Решение закрывает проблему П2 -- партнёрские API без единых политик безопасности и системного контроля (см. [README](../README.md)).

## 1. Требования к безопасности

1. **Шифрование каналов.** TLS 1.2+ для всех API-взаимодействий; mTLS между `smart-home-gateway-app` и платформой партнёра; WebRTC с шифрованием DTLS-SRTP для медиа-канала (видео/аудио домофона). Открытого HTTP-трафика к партнёру нет.

2. **Минимизация персональных данных в контрактах API.** Партнёру передаются только технические идентификаторы -- устройства, доступа, квартиры; ФИО, телефоны, адреса в контракты не включаются. Номера автомобилей передаются разово при регистрации доступа; биометрические шаблоны регистрируются на устройстве партнёра и в PropDevelopment не попадают. Состав полей API фиксируется в контракте и пересматривается при каждом изменении.

3. **Биометрия и видео -- на стороне партнёра.** Биометрические шаблоны (лица), записи видео и номера автомобилей хранятся и обрабатываются только в платформе партнёра. В PropDevelopment -- только идентификаторы доступа, факт согласия собственника и журнал событий. Биометрия -- специальная категория персональных данных (152-ФЗ, ст. 11): требуется явное согласие собственника; отзыв согласия в приложении инициирует удаление биометрии у партнёра.

4. **Журналирование операций.** Все команды открытия и изменения правил доступа журналируются (кто, когда, какое устройство, результат). Журнал хранится в PropDevelopment в режиме append-only (записи только добавляются) и недоступен партнёру; используется для внутреннего аудита и расследования инцидентов.

5. **Шифрование хранимых данных.** `smart-home-db` и её резервные копии шифруются (TDE -- прозрачное шифрование на уровне СУБД); доступ к БД по принципу минимальных привилегий, только для `smart-home-gateway-app`.

6. **Управление секретами.** Ключи, сертификаты mTLS, сервисные учётные данные (client credentials) и ключи подписи webhooks хранятся во внешнем хранилище секретов (Vault) с регулярной ротацией. Секреты не зашиваются в код и не передаются в конфигурации открытым текстом.

7. **Сетевая сегментация.** `smart-home-gateway-app` -- единственная точка исходящего управляющего и событийного трафика (egress) к платформе партнёра -- по белому списку доменных имён, IP-адресов и портов. Webhook-эндпоинты принимают соединения только с IP-адресов партнёра из белого списка. Медиа-трафик WebRTC (DTLS-SRTP) идёт напрямую между мобильным приложением и медиасерверами партнёра по белому списку доменов/IP.

8. **Требования к партнёру.** PropDevelopment -- оператор персональных данных, партнёр -- обработчик, обрабатывающий персональные данные по поручению оператора (152-ФЗ, ст. 6 ч. 3). Партнёр регулярно проходит аудит безопасности или пентест, уведомляет об инцидентах в течение 24 часов, соблюдает SLA доступности, допускает аудит обработки данных со стороны PropDevelopment и удаляет данные при расторжении договора.

9. **Защита webhook-эндпоинтов.** Проверка подписи каждого события, защита от replay-атак (повторного воспроизведения перехваченных запросов) через отметку времени и уникальный номер события (timestamp + nonce), ограничение частоты запросов (rate limiting), отклонение событий с неизвестными устройствами.

## 2. Протоколы аутентификации и авторизации

| Канал | Аутентификация | Авторизация |
| --- | --- | --- |
| Собственник -> мобильное приложение -> сервер PropDevelopment | OIDC / OAuth 2.0, authorization code + PKCE (защита кода авторизации для мобильных приложений) через `auth-service-1` (Keycloak) | JWT access token с правами (scopes) `smart-home:read`, `smart-home:control` |
| `smart-home-gateway-app` -> платформа партнёра | OAuth 2.0 client credentials + mTLS; сервисная учётная запись с минимальными правами; учётные данные в Vault | Серверные политики партнёра: доступ только к устройствам домов PropDevelopment |
| Платформа партнёра -> `smart-home-gateway-app` (webhooks) | Подпись тела события HMAC-SHA256 или JWS (подписанный JSON-токен), ключ в Vault; IP-адреса партнёра из белого списка | Приём только зарегистрированных типов событий и устройств |
| Медиа-канал (приложение <-> платформа партнёра) | Одноразовый короткоживущий токен сессии, выдаваемый сервером PropDevelopment после проверки доступа | Сессия привязана к конкретному устройству/звонку; WebRTC, шифрование DTLS-SRTP |

Модель авторизации (проверяется на каждый запрос):

- **Привязка «своя квартира/устройство».** Каждый запрос к устройству проверяется по привязке «пользователь -- квартира -- устройство» в `smart-home-db`. Запрос к чужому дому, подъезду или устройству отклоняется независимо от корректности аутентификации; платформа партнёра видит только устройства домов PropDevelopment.
- **Владелец** -- полное управление доступом к квартире (жильцы, гости, автомобили), просмотр журнала.
- **Жилец** -- управление своим доступом и открытие устройств своей квартиры.
- **Гость** -- временный доступ по приглашению владельца или жильца, только на срок действия приглашения.
- **Жизненный цикл доступа.** Гостевой доступ ограничен временем жизни (TTL) и отзывается автоматически; при смене собственника или продаже квартиры все права доступа отзываются; собственник может отозвать любой доступ немедленно из приложения.

## 3. Организация взаимодействия между системами предприятия и внешней платформой

1. **Anti-corruption layer.** `smart-home-gateway-app` изолирует домен PropDevelopment от модели данных партнёра: внутренние системы (`tenant-core-app`, мобильное приложение, CRM) работают только с канонической моделью PropDevelopment. Изменение API партнёра затрагивает только `smart-home-gateway-app`.

2. **Синхронные команды.** Открытие двери/шлагбаума, регистрация и отзыв доступа -- REST (JSON). Требования: идемпотентность (Idempotency-Key), таймауты, повторные попытки с экспоненциальной задержкой, circuit breaker (отключение вызовов при повторяющихся сбоях). Открытие -- интерактивная команда: при недоступности партнёра выполняется fail fast (мгновенный отказ без повторов), и пользователь видит ошибку в приложении. Регистрация и отзыв доступа при недоступности партнёра ставятся в очередь с гарантированной доставкой.

3. **Асинхронные события.** Звонок в домофон, открытие, тревога, распознанный номер автомобиля -- webhooks от партнёра в `smart-home-gateway-app`: нормализация, запись в журнал, публикация в Kafka для push-уведомлений мобильного приложения и аналитики.

4. **Управление API.** Версионирование API партнёра (URL-версии), контрактные тесты на совместимость, выделенный тестовый контур (sandbox) для интеграционных испытаний перед выводом в бой.

5. **Наблюдаемость.** Сквозное журналирование с корреляционными идентификаторами, метрики (доля неудачных команд, задержка открытия, задержка доставки событий), автоматические оповещения при деградации платформы партнёра.

6. **Данные для аналитики.** В хранилище данных (DWH) передаются только обезличенные или агрегированные события (без персональных данных, биометрии и видео).

7. **Отказоустойчивость.** Деградация сервисов умного дома не влияет на базовые функции ЖКУ (оплата, ремонт, информация от УК): интеграция изолирована в отдельном контейнере с собственной БД.
